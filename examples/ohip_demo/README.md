# OHIP demo

A plain `mix new` app with Oracle Hospitality (OHIP) clients generated by
Hearth from Oracle's public specs. It reads blocks and events from OPERA
Cloud, as a proposal flow does, and gets its tokens from OHIP's OAuth
API. Then it follows the clients from release 26.2 to 26.3. Hearth
reports what changed in the parts the app uses and whether any of it
breaks, then applies it. The generated functions stay the same and the
tests stay green.

Hearth comes in as a path dependency (`../..`), so the demo follows the
library in this repo. Steps 5 to 7 fetch Oracle's specs from GitHub, so
you need network for them.

```bash
mix deps.get
```

## 1. How the clients were made

Oracle publishes each OHIP API as its own Swagger 2.0 spec in
[`oracle/hospitality-api-docs`](https://github.com/oracle/hospitality-api-docs).
The demo uses three:
- Block (`blk.json`) and Event Management (`evm.json`), for the data;
- OAuth, for the token.

`.hearth.exs`, written before the first gen:

```elixir
[
  registry: %{
    "ohip_blk" => %{"26.2" => "…/52ca181…/rest-api-specs/property/v1/blk.json", "26.3" => "…/dd631fb…/rest-api-specs/property/v1/blk.json"},
    "ohip_evm" => %{"26.2" => "…/52ca181…/rest-api-specs/property/v1/evm.json", "26.3" => "…/dd631fb…/rest-api-specs/property/v1/evm.json"},
    "ohip_oauth" => %{"26.2" => "…/52ca181…/rest-api-specs/property/v1/oauth.json", "26.3" => "…/dd631fb…/rest-api-specs/security/v1/publishedoauth.json"}
  },
  integrations: [
    ohip: [
      sources: [blk: "ohip_blk@26.2", evm: "ohip_evm@26.2"],
      overrides: [
        patches: %{
          "/components/securitySchemes/bearerAuth" => %{"type" => "http", "scheme" => "bearer"},
          "/security" => [%{"bearerAuth" => []}]
        }
      ],
      headers: [
        "x-app-key": [resolve: {OhipDemo.Tenancy, :app_key}, options: [:chain]],
        "x-hotelid": [option: :hotel_id]
      ],
      base_url: [resolve: {OhipDemo.Tenancy, :gateway}, options: [:chain]],
      auth: [credential: [resolve: {OhipDemo.Tenancy, :token}, options: [:chain]]]
    ],
    ohip_oauth: [
      source: "ohip_oauth@26.2",
      headers: [
        "x-app-key": [resolve: {OhipDemo.Tenancy, :app_key}, options: [:chain]],
        enterpriseid: [resolve: {OhipDemo.Tenancy, :enterprise_id}, options: [:chain]]
      ],
      base_url: [resolve: {OhipDemo.Tenancy, :gateway}, options: [:chain]],
      auth: [credential: [resolve: {OhipDemo.Tenancy, :client_credentials}, options: [:chain]]]
    ]
  ]
]
```

- **`registry:`** gives each spec a shortcut. Each release points at the
  commit of its release tag, so `ohip_blk@26.2` always means the same
  file. The OAuth spec moved between the two releases, from
  `property/v1/oauth.json` to `security/v1/publishedoauth.json`; the
  shortcut hides that.
- **`sources:`** merges Block and Event Management into one integration:
  one client, one auth setup, one `OhipApi`. Each spec's base path
  (`/blk/v1`, `/evm/v1`) moves into its paths.
- **`patches:`** adds a bearer scheme. The data specs declare none; they
  only list `authorization` as a header parameter.
- **`ohip_oauth`** is the token endpoint, a separate integration. It
  uses HTTP basic auth with the chain's client ID and secret
  (`client_id:client_secret`).
- **Nothing comes from config.** A hotel chain shares one gateway, app
  key, client ID and secret, enterprise ID and scope; its hotels differ
  only by hotel ID. So every call passes the `chain:` and the
  `hotel_id:` it acts for. `OhipDemo.Tenancy` (`lib/ohip_demo/tenancy.ex`)
  resolves the gateway, the app key, the enterprise ID, the client
  credentials and the token from the chain. `x-hotelid` is the call's
  `hotel_id:`.

Then:

```bash
mix hearth.gen --integration Ohip \
  --tag "Block:get_block,get_blocks,get_block_range_info,get_block_room_rate_grid" \
  --tag "EventManagement:get_event,get_events_one_hotel,get_event_calendar" --yes
mix hearth.gen --integration OhipOauth --yes
```

With no source argument, gen read `sources:` / `source:` from each
entry and fetched the specs. It converted them to OpenAPI 3 and merged
Block with Event Management. It then picked 7 of their 138 operations,
plus the OAuth spec's one, `getToken`:

| File | What it is |
| --- | --- |
| `lib/ohip_demo/integrations/ohip.ex` | the raw Req client for the data: base URL, token and app key from `OhipDemo.Tenancy`, `x-hotelid` per call |
| `lib/ohip_demo/integrations/ohip/ohip_api.ex` | the behaviour your code calls: `get_blocks/1`, `get_block/3`, `get_block_range_info/3`, `get_block_room_rate_grid/3`, `get_event_calendar/2`, `get_events_one_hotel/2`, `get_event/3` |
| `lib/ohip_demo/integrations/ohip_oauth.ex` | the raw Req client for tokens: basic auth from the chain's client credentials, the gateway plus `/oauth/v1` |
| `lib/ohip_demo/integrations/ohip_oauth/ohip_oauth_api.ex` | its behaviour: `get_token/1` |
| `…/ohip_api/req.ex`, `…/ohip_oauth_api/req.ex` | the Req implementations |
| `test/ohip_demo/integrations/ohip_test.exs`, `ohip_oauth_test.exs` | each client's `Req.Test` test |
| `test/ohip_demo/integrations/*_external_test.exs` | live-API tests, yours to edit |
| `test/support/mocks.ex` | the Mox mocks for `OhipApi` and `OhipOauthApi` |
| `config/test.exs` | points both behaviours at their mocks in tests |
| `priv/hearth/ohip.yaml`, `ohip_oauth.yaml` | the specs pruned to these operations |
| `.hearth.exs` | the rest of each entry: module, checksums, which tags were selected, and the auth scheme |

`config/runtime.exs` stays empty: nothing in either client reads config.

## 2. Where the token comes from

Written by hand, next to the generated clients:

| File | What it is |
| --- | --- |
| `lib/ohip_demo/tenancy.ex` | `OhipDemo.Tenancy`: each value the clients ask for, from the call's `chain:` |
| `lib/ohip_demo/tenancy/tokens.ex` | one token per chain environment, kept in ETS until a minute before it expires |
| `lib/ohip_demo/application.ex` | starts the token table |

When a data call needs a token, `Tenancy.token/1` checks the cache.
On a miss it calls the generated `OhipOauthApi.get_token/1` with
`grant_type: "client_credentials"` and the chain's scope. That request
goes to the chain's gateway, plus `/oauth/v1`, with basic auth, the app
key and the enterprise ID. All of that comes from `Tenancy` again.

```elixir
chain = %{
  gateway: "https://…",
  app_key: "…",
  client_id: "…",
  client_secret: "…",
  enterprise_id: "…",
  scope: "…"
}

OhipDemo.Integrations.Ohip.OhipApi.get_block(block_id, "HOTEL1", chain: chain, hotel_id: "HOTEL1")
```

One token covers every hotel in the chain. Only `hotel_id:` changes
from call to call.

## 3. Test it

```bash
mix test
```

```
19 passed, 8 excluded
```

- **The two clients' tests** (`ohip_test.exs`, `ohip_oauth_test.exs`)
  drive each raw client through `Req.Test`, with no network. They pass the
  token, the app key and the base URL per call, so `Tenancy` never runs
  in them.
- **`test/ohip_demo/tenancy_test.exs`** stubs `OhipOauthApi` with its
  Mox mock. It checks that a token is requested once per chain and then
  cached, that chains don't share tokens, and that a token about to
  expire is fetched again. It also checks that a failed request raises.
  The last test calls `OhipApi.Req.get_block/3` through a `Req.Test`
  plug and checks the request: the chain's gateway, the cached bearer
  token, the app key and the hotel id.
- **The 8 excluded** are the live-API tests (`mix test --include
  external`). They read the chain from `OHIP_GATEWAY_URL`,
  `OHIP_APP_KEY`, `OHIP_CLIENT_ID`, `OHIP_CLIENT_SECRET`,
  `OHIP_ENTERPRISE_ID` and `OHIP_SCOPE`, and the hotel from
  `OHIP_HOTEL_ID` (`test/support/live_chain.ex`).

## 4. Check it's in sync

```bash
mix hearth.diff --all
```

```
hearth.diff: ohip: no drift against blk: ohip_blk@26.2, evm: ohip_evm@26.2.
hearth.diff: ohip_oauth: no drift against ohip_oauth@26.2.
```

`diff` re-prunes each source and compares it with the pruned spec in
`priv/hearth/`. It writes nothing and exits non-zero on drift, so it
belongs in CI.

## 5. Oracle ships 26.3

Point every source at the new release in `.hearth.exs`:

```elixir
sources: [blk: "ohip_blk@26.3", evm: "ohip_evm@26.3"],
…
source: "ohip_oauth@26.3",
```

and ask what changed:

```bash
mix hearth.diff --all
```

```
hearth.diff: ohip has drifted from blk: ohip_blk@26.3, evm: ohip_evm@26.3.

blk, evm changed since the last gen or sync.

Operations:
  ~ get /blk/v1/blocks (getBlocks): query parameter blocksWithRoomInventory added
  ~ get /blk/v1/hotels/{hotelId}/blocks/{blockId} (getBlock): query parameter roomAllocationCriteria: []: enum gains ChildRates
  ~ get /blk/v1/hotels/{hotelId}/blocks/{blockId}/roomRateGrid (getBlockRoomRateGrid): query parameter roomAllocationCriteria: []: enum gains ChildRates

Schemas:
  ~ allocationType: enum gains ChildRates
  ~ blk_depositPolicyType: deadline: $ref policyDeadlineType → blk_policyDeadlineType  [breaking]
  + blk_policyDeadlineType
  ~ blk_resCancelPenaltyType: deadline: $ref policyDeadlineType → blk_policyDeadlineType  [breaking]
  + blockGridChildRatesType
  ~ cancelPenaltyType: deadline: $ref policyDeadlineType → blk_policyDeadlineType  [breaking]
  - policyDeadlineType  [breaking]
  ~ roomGridDetailsType: property childRate added

11 changes (4 breaking). Apply them with:

  mix hearth.regen ohip --sync

ohip: policyDeadlineType is no longer the same in every source, so each source's
copy now carries its key — and shows as a rename in the drift. To keep
the plain name for the source whose copy is unchanged, add to the entry
in .hearth.exs:

    overrides: [shared: %{"schemas/policyDeadlineType" => :blk}]

hearth.diff: ohip_oauth: no drift against ohip_oauth@26.3.

The source changed since the last gen or sync.
```

Only the operations the app uses, and the schemas they reach, are
compared. The rest of Oracle's specs can change freely.

- **`ohip_oauth`:** the spec file moved and its text changed, but
  `getToken` didn't, so there's no drift.
- **`ohip`:** the 4 breaking changes aren't an API break. Block and
  Event Management both define `policyDeadlineType`, and on 26.2 the two
  copies were identical, so the merge kept one. On 26.3 they differ, so
  the merge has to keep both, each named after its source
  (`blk_policyDeadlineType`). That shows up as a rename. The advice at
  the end says which source to keep the plain name for.

## 6. Keep the shared name

Add the suggested line under `ohip`'s `overrides:` in `.hearth.exs`:

```elixir
overrides: [
  shared: %{"schemas/policyDeadlineType" => :blk},
  patches: %{…}
],
```

and diff again:

```bash
mix hearth.diff ohip
```

```
Operations:
  ~ get /blk/v1/blocks (getBlocks): query parameter blocksWithRoomInventory added
  ~ get /blk/v1/hotels/{hotelId}/blocks/{blockId} (getBlock): query parameter roomAllocationCriteria: []: enum gains ChildRates
  ~ get /blk/v1/hotels/{hotelId}/blocks/{blockId}/roomRateGrid (getBlockRoomRateGrid): query parameter roomAllocationCriteria: []: enum gains ChildRates

Schemas:
  ~ allocationType: enum gains ChildRates
  + blockGridChildRatesType
  ~ roomGridDetailsType: property childRate added

6 changes, none breaking.
```

That's the real 26.2 → 26.3 change for a proposal flow. Child rates
reach the block's room grid, and `getBlocks` gains a filter. No
operation was added or removed.

In CI, decide what fails the build:

```bash
mix hearth.diff ohip; echo $?                      # 1: any drift fails
mix hearth.diff ohip --fail-on breaking; echo $?   # 0: additive drift is only a notice
```

## 7. Move to 26.3

```bash
mix hearth.regen --all --sync --yes
```

`--sync` re-prunes each source, lists the changes it applied, and
regenerates the clients. See what changed:

```bash
git diff --stat .
```

- `priv/hearth/ohip.yaml`: the 6 changes, as a diff you can review.
- `priv/hearth/ohip_oauth.yaml`: the OAuth spec's new descriptions and
  version label.
- `.hearth.exs`: the new sources and their checksums.
- `…/ohip_api.ex` and `…/ohip_oauth_api.ex`: their `## Source` footers,
  and the OAuth API's new description.

No function changed. New fields, enum values and query parameters all
go through the functions the app already has, for example
`get_blocks(params: [blocksWithRoomInventory: true], chain: chain, hotel_id: "HOTEL1")`.

```bash
mix test   # still 19 passed
```

Nothing is left to apply:

```bash
mix hearth.diff --all             # no drift
mix hearth.regen ohip --dry-run   # No proposed content changes!
```

## Hand-edited files

To change a generated file and keep the change, put `hearth:owned` in
its `@moduledoc`:

```elixir
@moduledoc """
Raw Req client for the Ohip integration.

hearth:owned
"""
```

`regen` and `--sync` then skip it:
`* skipping lib/ohip_demo/integrations/ohip.ex (hearth:owned)`.
`hearth:collaborating` makes them ask first, file by file.
