# Stripe demo

A plain `mix new` app with a Stripe client generated by Hearth. It shows
how the client was made from Stripe's published OpenAPI spec, what got
generated, and how to keep it in step as Stripe ships new releases.

Hearth comes in as a path dependency (`../..`), so the demo follows the
library in this repo.

```bash
mix deps.get
```

## 1. How the client was made

Stripe's spec has 587 operations and none of them carry a tag, so
`--tag` has nothing to select from. `.hearth.exs` tags the ones this demo
uses, with overrides written before the first gen:

```elixir
stripe: [
  overrides: [
    tags: [
      Customers: ["get /v1/customers", "post /v1/customers", "get /v1/customers/{customer}"],
      Subscriptions: ["/v1/subscriptions*"]
    ]
  ]
]
```

Each entry is a path glob (`*` matches anything, `/` included), a method
plus a path, or an operationId. Then:

```bash
mix hearth.gen stripe@2026-04-22.dahlia --tag Customers --yes
```

fetched that pinned release from Stripe's GitHub repo, picked the three
`Customers` operations out of 587, and wrote everything in this
directory that `mix new` didn't:

| File | What it is |
| --- | --- |
| `lib/stripe_demo/integrations/stripe.ex` | the raw Req client — base URL `https://api.stripe.com/v1` |
| `lib/stripe_demo/integrations/stripe/stripe_api.ex` | the behaviour your code calls: `get_customers/1`, `post_customers/1`, `get_customers_customer/2` |
| `lib/stripe_demo/integrations/stripe/stripe_api/req.ex` | the Req implementation |
| `test/stripe_demo/integrations/stripe_test.exs` | the client's `Req.Test` test |
| `test/stripe_demo/integrations/stripe_external_test.exs` | live-API tests, yours to edit |
| `test/support/mocks.ex` | the Mox mock for `StripeApi` |
| `config/test.exs` | points `StripeApi` at the mock in tests |
| `priv/hearth/stripe.yaml` | Stripe's spec pruned to these three operations |
| `.hearth.exs` | the rest of the entry: module, source, checksum, base path, and which tags were selected |

### Where `stripe@2026-04-22.dahlia` comes from

Hearth keeps a registry of known API specs, so you don't have to find
the spec file yourself. `stripe@2026-04-22.dahlia` is a shortcut in it:
it resolves to Stripe's own published spec at that release,
`https://raw.githubusercontent.com/stripe/openapi/v2266/openapi/spec3.yaml`.
A shortcut also names the integration (`Stripe`), which is why the
command above needs no `--integration`.

A shortcut can be written several ways:

- `stripe@2026-04-22.dahlia` — one exact release, pinned to a tagged URL.
- `stripe@dahlia` — an alias for the newest release in the `dahlia`
  family; `stripe@2026-04-22` — an alias by date.
- `stripe` or `stripe@latest` — Stripe's spec as it is right now; it
  moves as Stripe pushes.

```bash
mix hearth.gen --list          # the shortcuts Hearth knows
mix hearth.gen stripe --list   # Stripe's versions
```

A pinned release keeps the demo reproducible. `.hearth.exs` records the
shortcut as `source:`, and every `diff` and `--sync` resolves it again.
Your project can add its own shortcuts, with the same shape, under
`registry:` in `.hearth.exs`. A file path or a URL works as a source
too.

## 2. Test it

```bash
mix test
```

runs `test/stripe_demo/integrations/stripe_test.exs`, which drives the
raw client through `Req.Test` — no network. (It only checks that a
request gets through for now: see the auth gap below.)

```bash
mix test --include external
```

also runs `test/stripe_demo/integrations/stripe_external_test.exs`: one
test per operation against the real API, with placeholder arguments to
replace. Hearth creates that file once and never overwrites it.

In your own code you'd call the behaviour,
`StripeDemo.Integrations.Stripe.StripeApi.get_customers(params: [limit: 3])`,
and stub it in tests with `StripeDemo.Integrations.Stripe.StripeApi.Mock`.

## 3. Check it's in sync

```bash
mix hearth.diff stripe
```

re-prunes the source in `.hearth.exs` — the pinned
`stripe@2026-04-22.dahlia` — and compares it with
`priv/hearth/stripe.yaml`:

```
hearth.diff: stripe: no drift against stripe@2026-04-22.dahlia.

The source is unchanged since the last gen or sync.
```

`diff` writes nothing and exits non-zero on drift, so it belongs in CI.

## 4. Compare against any version

`--source` compares the integration against another spec, without
touching `.hearth.exs`. It takes anything a source can be: another
pinned release, the floating `stripe@latest`, a URL, or a local file.

```bash
mix hearth.diff stripe --source stripe@2026-03-25.dahlia   # an earlier release
mix hearth.diff stripe --source stripe@latest              # Stripe's latest spec
```

Against `stripe@latest`:

```
hearth.diff: stripe has drifted from stripe@latest.

It differs from the source recorded at the last gen or sync.

Operations:
  ~ post /v1/customers (PostCustomers): request body application/x-www-form-urlencoded: tax_id_data[].type: enum gains ic_nif

Schemas:
  ~ account_business_profile: property specified_commercial_transactions_act_url added
  ~ account_capabilities: property bizum_payments added
  ...
  ~ card: property iin removed  [breaking]
  ...

247 changes (30 breaking). To apply them, point `source:` at stripe@latest in .hearth.exs and run:

  mix hearth.regen stripe --sync
```

That's every change to the three operations and to the schemas they
reach, with the breaking ones marked. Run `mix hearth.gen stripe --list`
to see the versions Hearth knows.

## 5. Move to another version

In `.hearth.exs`, change `source:` to the version you want, then
re-prune and regenerate:

```bash
mix hearth.regen stripe --sync
mix hearth.diff stripe        # in sync again
```

`--sync` rewrites `priv/hearth/stripe.yaml` and regenerates the client,
listing what it applied. To pick up more operations, add patterns to the
overrides, or tags to `tags:`, and `--sync` again.

## Known gap: auth

Stripe's spec lists HTTP basic auth first (the secret key as the
username) and bearer second. Hearth wires bearer and API-key auth but not
basic, and picks the first scheme, so the raw client is generated without
auth and with a `TODO`. Choosing `bearerAuth` is on the way. Until then,
pass the key yourself:

```elixir
StripeDemo.Integrations.Stripe.StripeApi.get_customers(auth: {:bearer, "sk_test_…"})
```
